# Roadmap model - brief and orchestrator's reflection (2026-10-07)

Context for a design discussion with Kris Brown in the state-of-play review of the Knowledge Islands Agora (21 repositories + chezmoi; 78 open roadmap records). Sources: theme map `~/.local/state/claude-bg/gov-020/themes.report.md` (+ `theme-map.json` here), horizon x status matrix `~/.local/state/claude-bg/gov-020/matrix.report.md`, themes-apply report `~/.local/state/claude-bg/gov-020/themes-apply.report.md`, state-of-play checkpoint `ki-arcadia-principal/+/_CHECKPOINTS/state-of-play.md`, roadmap standard `ki-agentic-harness/skills/change-management/ki-work-roadmap/` (+ ki-next, ki-plan, ki-accept references), kit-legal Command Centre `kit-legal/Pillars/Command Centre/Command Centre Guide.md`.

## 1. What the discussion established

- **Today's `theme:` field is per-repository and mostly says where/what kind of work** (harness: governance-consistency 26 of 36; chezmoi: user-environment 11 of 11; cli, operations, site-experience...). It carries little information and does not align across repositories. Kris: it is really closer to `component`.
- **Twelve cross-repository themes were agreed today** from a read of all records: baseline, techne, estate-factorisation, paperclip-bootstrap-and-recovery, territories-and-trades, delta-evaluation, standards-upkeep, island-model-and-tending, knowledge-acquisition, workstation-hygiene, specifications (paused), website (paused).
- **Kris liked restructuring them into tool vocabulary:**
  - Initiative "Platform foundations": Projects Baseline rollout, Estate factorisation; upkeep standards-upkeep.
  - Initiative "Techné": Projects Agent host, Paperclip bootstrap and recovery, Delta evaluation.
  - Initiative "Knowledge Islands model": Projects Island model and Tending, Territories and trades, Knowledge acquisition, Specifications (paused), Website (paused).
  - Initiative "Rig": upkeep workstation-hygiene.
  - A thread = a Project; its checkpoint = the Project update (health + narrative: one decision and its test, the facts it needs, one next step - the delta-evaluation shape Kris endorses). state-of-play = the review across Initiatives.
- **Command-centre idea stage** (kit-legal: Areas own scope, Items own live state, Working Notes hold developing material and never own status, generated views never hand-kept): Kris does not want ideas forced into records too early - the theme map found ~10 records captured too early, and themes with several records nobody can act on. Ideas mature in the Project (checkpoint/project documents) and become an Issue/record once they can state goal, context and boundary.
- **Horizon = when (priority, like cycles); status = how far (progress).** No cap on Now: "it's about intent". Matrix findings: Now and Next are indistinguishable today; nothing gates next -> now; the standard says deferral preserves status but the checker fails any non-draft outside now/next, so paused in-progress work is forced to sit in Now; no route for failed review or replan.
- **Closure evidence:** four duplicate closures Kris approved were all blocked by the rules - no plain cancel for adopted work (must detour back to Triage and be "rejected"), and no duplicate/merge across repositories.
- **Tool mapping (Linear/Jira/GitHub):** repository = Team (ID prefix); record = Issue (`task_links` exists; harness FND-014 would build Issues/Linear adapters); Project = finite cross-team outcome with status, lead, target, health and updates; Initiative groups Projects; Component = Jira Components / Linear label group; Type = issue type; status = workflow state (Triage, Backlog, Todo, In Progress, In Review, Done, Canceled, Duplicate); horizon ~ Cycle (now, next) + priority/backlog; waiting/parked have no native home. Records stay canonical; tools are one-way projections plus links.
- **Naming trap:** the standard's `area` already means the ID issuing code (`GOV` in KI-HARNESS-GOV-109).

## 2. Kris's proposal (verbatim intent)

> I'm thinking that we really get some better fields onto roadmaps that say what they are and we migrate them all.
> Part of the standard: **kind** (the kind of item it is); **artifact** (similar to the Linear labels below, but applied to this domain); **horizon**: now, next, soon, future, hold, triage - this is like cycles; **status**: as is, but waiting-for/parked are always hold horizon, and triage is both a horizon and a status???; **purpose**: probably useful too, from Linear.
> Territory defined: **initiative**, **project**.
> Repository defined: **component**: CLI, etc.

## 3. Orchestrator's reflection (Opus) - for Fable to challenge

1. **The three-tier ownership is right**: portable fields in the harness standard; initiative/project vocabulary owned once at territory level (Arcadia, as a registry the checker can resolve); component vocabulary declared per repository in `.ki.toml`. This is exactly Linear's Workspace / Team split and lets `ki` build both views: by repository (ownership) and by initiative/project (intent).
2. **Keep kind, artifact and purpose orthogonal.** HNR's Artifact list mixes output type (Application, Lib, Docs, Config, Data, Tool, Agentic, Ops) with nature of work (Tasks, Correction, Useability), and Correction duplicates Purpose/Corrective. Cleaner:
   - **kind** = the nature of the item (Linear/GitHub issue type): deliver, decide, investigate, verify, review (recurring housekeeping run). Command-centre wait/chase are holds, deadline/event are calendar - not kinds. `decide` and `investigate` answer the "captured too early" problem: many records are decisions or investigations dressed as delivery.
   - **artifact** = what it produces, KI domain: standard, skill, cli, mcp, library, application, infrastructure, configuration, knowledge (KB notes, decisions, Pillars), documentation, data, none (decide/investigate outcomes).
   - **purpose** = why: HNR's list nearly verbatim - feature, enabler, debt, corrective, process; "solution" (customer-specific) maps to adoption into a specific island; one word to agree.
3. **Triage should be a status, not a horizon.** Kris's "both???" is the tell. In Linear, Triage is a workflow state; a triage item has no priority yet. Proposal: status = triage, draft, ready, in-progress, awaiting-review, done, cancelled (with `duplicate_of` allowed across repositories by canonical ID). Horizon = now, next, soon, future, hold - only for adopted work; unset while triage. That removes the dual meaning and gives the missing cancel and cross-repository duplicate.
4. **hold replaces waiting-for and parked**, with `hold: {reason: waiting-for | parked, condition: ..., resume: now|next}`. A hold may keep a ready or in-progress status (paused work keeps its baseline), resolving the checker contradiction. Linear: hold -> label or Blocked state.
5. **Status x horizon after the change:** triage => no horizon; draft anywhere adopted; ready/in-progress in now, next or hold; awaiting-review in now; done/cancelled terminal (horizon irrelevant). No Now cap (intent).
6. **project vs initiative on a record:** store `project` only and derive `initiative` from the registry, to avoid drift; records with no project (upkeep) carry `initiative` directly plus an upkeep label. Linear can't attach an issue to an initiative without a project, so upkeep may need standing "continuous" projects in the projection - open question.
7. **component** absorbs today's `theme` values where they really are components (cli, operations, controller, execution-fabric, site-experience, user-environment). `governance-consistency` is not a component (closer to purpose = process) - migration needs per-record judgement, proposed by agent and approved by Kris.
8. **Rename the ID `area`** (issuing code) to avoid the collision with Linear/HNR "Area" (= component), e.g. `series` or `prefix`; or leave it as an internal term. Open.
9. **Checkpoint = Project update; state-of-play = Initiative review; idea stage = project documents/ideas section in the Project.** A record is created when an idea can state goal, context and boundary - not before.
10. **Migration:** design note -> harness standard records (fields, statuses, horizons, checker) -> tools-ki (checker, `ki roadmap list --by project|initiative`, migration helper) -> Arcadia initiative/project registry -> per-repository migration of all records (open and retained done), mapping proposed by agents, approved by Kris -> later Linear projection (FND-014). The paused specifications repository may be the natural long-term home for the model, but it is parked.
11. **Terminology:** "work record" vs "Issue" undecided; repositories keep `docs/roadmap/`.
