### Part A - recommendation

Recommend **two-phase publication to one canonical remote main, with a unique reservation nonce and exact ownership verification**, if Kris chooses to replace the current single-checkout rule. This is the smallest change compatible with today's advance-before-record convention and the request to prove reservation before a record exists. A ledger increment plus a successful push exit alone is insufficient. Keep one local writer lock per checkout; different authorised checkouts compete only at the canonical ref. No service, distributed lease, gap reclamation or standing general push permission is needed.

1. Under explicit publication authority, start from a clean, level primary checkout and fresh canonical ref. Lock the local writer, reread the actual ledger and issuing area, allocate current high-water plus one, generate a fresh random nonce, and make a normal-hook explicit-path ledger-only commit. Put the nonce and repository/area/serial binding in a structured commit trailer; that changes commit identity without adding a sidecar or violating ledger-only file scope. The proposed identifier is not owned until publication is verified.
2. Publish by an ordinary non-force fast-forward update. Git's receive-side ref transaction compares its expected old object and serialises the winning update. Two sibling candidates cannot both fast-forward onto main: one wins; the other fails rather than resolving the collision by merge. This is branch-wide contention, including unrelated code commits. A normal push is not a promised application-level lease on a previously fetched HEAD: inspect the actual parent and accepted history, rather than assuming the shell's earlier read is the exact server precondition.
3. Require the exact nonce-bearing candidate to be reachable from canonical main, with the intended monotonic ledger delta from its parent (one next serial, or an explicitly burned rejected-attempt gap), correct namespace and serial, and no duplicate issuance. Verify the resulting ref/receipt, not just exit zero or equal high-water content. Two identical commits can have the same object ID when parent/tree/message/author/committer/timestamps match; the second push can say already up to date. A later writer can also mistake an earlier equal ledger value for its own. A unique per-attempt nonce plus exact accepted-commit proof prevents honest writers from both claiming such a no-op. It is concurrency provenance, not authentication against hostile authorised writers.
4. On a definitively rejected reservation, retain evidence of rejection but discard its unpublished allocation; refresh, reconstruct the ledger-only candidate from current main with a fresh number and nonce, and rerun hooks. Never rebase, merge/cherry-pick the losing reservation or reuse its rejected number. If another writer reserved N, the loser uses greater than the new high-water, never N. If unrelated code won and N is still unused, deliberately skip N: publish a new reservation for at least max(current high-water + 1, rejected N + 1), documenting that burned gap. A transport failure is ambiguous: reconcile the original nonce against canonical history before retrying or allocating again.
5. Only after proven ownership create the canonical record, preserving the reservation's identifier. Its publication references the accepted reservation in a structured commit trailer/receipt. Other writers may advance main meanwhile: fresh-read record absence, ownership and payload dependencies, reconstruct the record-only publication on latest main and push fast-forward. Do not blindly rebase a rejected payload or claim it is remotely delivered before its own receipt. An already-existing record requires exact own receipt/payload equality or explicit conflict handling, never overwrite. Once the reservation is accepted, its number stays owned even when its later payload push loses; rejection of the payload does not reopen allocation.

**Crash and immutability rules.** A crash after reservation leaves a permanently burned slot; gaps are valid. Resume only with the exact accepted nonce/commit proof, otherwise allocate afresh. No timeout, reuse, high-water decrement or abandoned-slot reclamation. Published reservation commits must remain in canonical history; reject history rewrite and rollback of the high-water, including a normal revert that lowers it. Resume by another agent/host needs an explicit owner handoff of the proven reservation, not nonce discovery mistaken for permission. Canonical-ref protection and all-writer conformance are prerequisites; Git alone does not enforce ledger semantics. Existing re-keyed history must preserve its issuance provenance through approved namespace changes.

**Other roadmap writes.** Number reservation does not solve stale capture payloads, lost plan edits, acceptance or deletion races. Each mutation must bind the exact expected source blob/revision and relevant dependencies, preserve id/created_at, advance updated_at, and leave baseline null until authorised implementation. Lock local read-through-commit; immediately compare the source used to compose the change, not a snapshot first taken after composition. On a rejected publication, reread/revalidate gates and regenerate against the new revision; same-record changes need semantic reconciliation and changed acceptance candidates need renewed review. Preserve committed terminal closure before a separate deletion-only publication, reference/trade preflight, ordinary hooks and explicit owned paths. Raw manual skill writes must use the same preflight/transaction contract. Offline/unreachable remote, dirty/staged checkout, divergence, unknown history or missing permission fails closed; report/propose in runtime only, with no remote reservation claim, stash/reset or hidden network retry.

**Atomic alternative.** A single ledger-plus-record commit published through the same canonical-ref compare-and-swap is equally collision-safe for published records when losers regenerate identifiers and neither local candidate is treated as reserved. The current standard's claim that coupled publication is inherently unsafe applies to independent local histories without a shared acceptance point; remote arbitration closes that window. Atomic publication uses one commit/push and no abandoned pre-reservation slots, so it is simpler if provisional local records are acceptable. It does not satisfy the proposed requirement that ownership be proven before record creation and would explicitly replace today's two-commit ordering. Choose it only if Kris prefers that trade-off. Do not build both protocols by default.
