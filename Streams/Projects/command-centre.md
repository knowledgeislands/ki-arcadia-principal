# Command centre

## Outcome

The Observatory on each host is Kris's command centre: its Instruments, Beacon and Bridge; a read-only Sessions view as the pane of glass, showing token use per run and per thread and each account's 5-hour and 7-day windows; and later a messaging endpoint on each host, linked to the others over the tailnet. It runs one shared vocabulary and model for the coordination concepts across the estate - the master and Project threads, Initiatives and Projects, checkpoints, decisions logs, marks, Needs and background agents in Knowledge Islands; the Command Centre in legal-principal; the HNR Council in hnr-principal; the Convenor role and Paperclip Coordination project; and the personal-principal Project Portfolio. [[ways-of-working]] keeps the event contract, including its advertisement and usage fields, and `apps-observatory` keeps the product. The test: the glossary names each concept once, every surface states whether it is a projection or an owner, and Kris can see every agentic session on a host, with its token use and the account windows, at a glance in one read-only view.

Kris set this Outcome on 2026-10-14: "Keep one Project, command-centre, and reshape its Outcome as the Observatory on each host: Instruments, Beacon and Bridge; a read-only Sessions view as the pane of glass, showing token use per run and per thread and each account's 5-hour and 7-day windows; later a messaging endpoint on each host linked over the tailnet, with ntfy as the stopgap question in Notes."

This Project sits in [[knowledge-islands-model|Knowledge Islands model]].

### Ideas for evaluation, 2026-10-14

Dispatched by the state-of-play thread from Kris's words of 14 October 2026. They are ideas, not records. On 2026-10-14 Kris kept them in this one Project and reshaped its Outcome around them (OBS-MERGE, in the [areas-proposal](<../../+/_THREADS/state-of-play/areas-proposal.report.md>) report); measuring token use moved to [[ai-observability|AI observability]].

- **Open question: ntfy as the stopgap.** Until each host has its own messaging endpoint linked over the tailnet, does ntfy on `sol`, tailnet-only, serve as the interim cross-host channel, each Observatory subscribing outbound and relaying to its page over Server-Sent Events? Kris: ntfy is "decent but maybe not long term". Any tailnet listener is connection-critical and follows the tailnet-only listener pattern in `tools-rig`.
- **Idea: the Observatory as host command centre.** Kris asked whether command-centre and the Observatory are "one thing" and pointed to the bridge docs. The Observatory's own decision on Observatory, Beacon and Bridge makes Instruments read-only, the Beacon the attention ranker and the Bridge the governed command side, with Rig as "the first Bridge aspect". The proposal reads this Project as the model and the Observatory on each host as the surface where it runs: Instruments, Beacon, Bridge and the state-of-play view as an Instrument, with `apps-observatory` keeping product ownership. Evidence: [areas-proposal](<../../+/_THREADS/state-of-play/areas-proposal.report.md>).
- **Idea: inter-agent pub-sub communication.** Kris: inter-agent pub-sub is its own topic; ntfy is "decent but maybe not long term"; consider "a decentralised system per host with the Observatory as command centre for host and cross-tailnet communication"; the tailnet is the VPN substrate, not the interaction mechanism. Open questions: whether ntfy on `sol`, tailnet-only, serves as the interim cross-host channel (each Observatory subscribing outbound and relaying to its page over Server-Sent Events, chosen over WebRTC on 2026-10-13), and what the decentralised per-host endpoint, peered over the tailnet, should be. Any tailnet listener follows the tailnet-only listener pattern in `tools-rig` and is connection-critical. The event contract the transport carries stays with [[ways-of-working]]. Evidence: [sync-telemetry](<../../+/_THREADS/state-of-play/sync-telemetry.report.md>), stage 3.
- **Idea: a single pane of glass, with agents advertising themselves.** Kris: "I'm wondering though if the observatory can also see those agentic sessions. I'm not suggesting that I want that to become the graphical user interface for the harness at this point ... but I think some kind of single pane of glass for what's going on like this would be really, really useful as well. And then, obviously, this would allow things like agents to advertise themselves." The proposal widens this Project's read-only view from threads to every agentic session on the host, as a read-only "Sessions" Observatory Instrument: `ki agent` runs, threads and agents with their status lines, and live Claude Code sessions from `~/.claude/sessions/` by metadata only (name, repository, busy or idle, start time), never transcripts. Codex shows as "not observable live" until it has a registry. It is never a harness GUI: no prompt box, no launching, stopping or resuming; acting on a session would be a later Bridge aspect with its own decision. No cross-host view in the first slice. Zed stays where Kris talks to sessions, Paperclip stays company coordination and Delta stays with [[delta-evaluation]]. Evidence: [areas-glass](<../../+/_THREADS/state-of-play/areas-glass.report.md>).
- **Idea: token economics in the glass.** Kris: "Another key aspect of this whole command centre piece, the observatory, OTLP, the pub sub mechanism, all of that good stuff, is that we also need to think about token economics as part of it." This Project's part is showing it: per-run and per-thread token totals beside each session, each account's 5-hour and 7-day windows with reset times (read from claude-swap and CodexBar, adding no new provider call), and Beacon attention when a window passes 90 % or a run stops on a limit. Measuring belongs with [[ai-observability|AI observability]] under [[platform-foundations|Platform foundations]], and acting (fallback and concurrency) with [[ways-of-working]]. Evidence: [areas-tokens](<../../+/_THREADS/state-of-play/areas-tokens.report.md>).

But ... observability over those things so I can see when agents are waiting, whether they've got sub-agents that they've subbed out to ... like looking down on ... from the tower in your castle and seeing all the villagers moving around ... a little bit like air traffic control".
