## The responsive coordinator

This principle sits above the six units. It is non-negotiable, it is in Kris's words, and every change this design makes carries it. Kris's message to threads, verbatim (2026-10-13):

> It's imperative that you do not do the work directly and that you delegate that work to subagents so that you remain responsive. And if I send you a message, it doesn't preempt any work that you are already doing. This is a fundamental requirement of the delegation capability.

As rules:

1. **The thread never does substantive work itself.** A coordinating thread dispatches, decides with Kris and reports. Nothing else.
2. **Every unit of work goes to a detached background agent.** Through `ki agent`, in its own session, surviving anything that happens to the thread. An in-session subagent is not a background agent.
3. **An owner message never pre-empts work in flight.** It steers: the thread folds it into running and queued work and answers within one short turn. A background agent stops only when Kris names it and says stop.

Kris's answers that the main thread coordinates, that he leans to a lower coordinator model and that responsiveness needs checkable rules lead here; his responsiveness requirement makes it fundamental. Kris has had to paste the message above into threads repeatedly, which is the failure this section exists to end: a thread that does the work itself is unresponsive while it does it, so Kris's next message either waits or, by interrupting, destroys the work. Delegation is what makes a thread interruptible without loss.

### Why the written rules are not holding

The Coordinator responsiveness section of the [`ki-delegation` background-run standard](</Users/krisbrown/workspaces/knowledge-islands/ki-agentic-harness/skills/governance/ki-delegation/references/standards-background-runs.md>) has said most of this since revision `70606d77`, with a turn budget, a never-in-thread list and a self-check. It is not holding, and the reasons split into the runtime's mechanics and the model's behaviour. Everything below marked _inferred_ was not confirmed from documentation or the binaries; the rest was checked on 2026-10-13 against `claude --help` (Claude Code 2.1.287), `codex --help` (Codex CLI 0.162.1), the hook events and user-facing strings each binary carries, the user-level hook configuration on this machine and `tools-ki`'s runtime adapters.

**Mechanics.**

- _A turn is the unit of attention._ In both runtimes the model works in turns: one owner message, then a sequence of model steps and tool calls until the model stops. A tool call blocks the turn until it returns. The thread cannot read or answer anything while a turn is running, so a turn that reads a 300-line standard, drafts a report and runs an audit leaves the thread unresponsive for the whole of it.
- _What happens to Kris's message mid-turn._ Claude Code queues a message typed during a turn and offers two ways out: leave it queued, so it is delivered when the turn ends, or press Enter to send it immediately; Escape cancels the in-flight request, which the transcript records as `[Request interrupted by user]`. The sent-immediately path is delivered at the next step boundary and folds into the current turn (_inferred_ from the queue strings; not documented locally). Either way Kris pays: a queued message waits for work that should not be in the thread, and an interrupt kills the step in flight, including any in-session subagent, whose work is lost. Codex exposes `codex queue --thread <session> --message <text>` for the same purpose, and its binary carries steering and interrupt strings and an `Interrupt` hook event; that its interactive session queues typed messages the same way is _inferred_.
- _Detached agents are the only work an interrupt cannot touch._ `ki agent launch` runs `claude -p` or `codex exec` as a separate process in its own session, standard input from `/dev/null`, output to the run log (`tools-ki/src/core/agent/runtimes.ts`). Nothing Kris does in the thread reaches it. The in-flight work Kris's messages have been pre-empting was therefore, by construction, work the thread was doing itself or through in-session subagents.
- _What survives compaction._ Claude Code compacts a long context into a summary at a `compact_boundary`; a `PreCompact` hook can add material to preserve, and `SessionStart` fires again after compaction (the `compact` matcher is in Claude Code's published hook documentation and _not verified locally_). Codex has `PreCompact` and `PostCompact` events. The system prompt, `CLAUDE.md` with its imports and any hook output are re-supplied on every turn and survive; what the thread learned by reading a file, the background-run standard included, survives only as far as the summary keeps it. The opener's role line survives only if the summary happens to carry it. The checkpoint survives because it is a file.
- _What survives a model switch._ Switching model mid-session keeps the transcript and the system prompt, so the rules are present, but a different model weighs them differently, and the lighter the model the more it needs the rule in front of it rather than behind it (_inferred_).
- _Hooks are the only per-turn injection either runtime offers._ Claude Code's `UserPromptSubmit` hook runs a command or prompt on every owner message and adds its output to the context the model sees for that turn; the user-level `settings.json`, managed in chezmoi, already registers `SessionStart`, `PreToolUse`, `PostToolUse` and `Stop` hooks that the harness ships. Codex 0.162.1 has the same event, `UserPromptSubmit` with `additionalContext` output, behind its `hooks` feature, which this machine's `config.toml` already enables, configured in `~/.codex/hooks/hooks.json`; no Codex hook is registered today. Nothing else restates a rule at the moment Kris speaks.

**Behaviour.**

- _The urge to just do it._ Given a task it can see how to do, the model does it. Delegating costs a brief, a launch, a wait and a recap, each a tool call with a chance of a permission prompt; doing it is one read and one edit. The rule asks the model to take the path that looks slower, every time, with no mechanical penalty for taking the other.
- _Loaded is not salient._ The standard is read at bootstrap and again under the refresh rule. By the thirtieth turn it is thousands of tokens back, behind reports, diffs and Kris's own messages. The system prompt and `CLAUDE.md` are re-supplied each turn; the standard is not. The self-check, "before each tool call, ask whether it is a quick check", has nothing to prompt it, so it fires when the model happens to remember.
- _Drift compounds._ Each in-thread step makes the next more natural: having read the file, editing it is easier than describing it to an agent. After a compaction the summary records what the thread did, not what it was told not to do, so a thread that has drifted restarts from the drifted state.
- _The standard's own softeners._ "A handful of quick tool calls", "one or two short files" and "about a minute" are judgement calls that a model mid-task resolves in favour of continuing. Only "never in-thread" and "always through a detached waiter" are hard, and they are two bullets in a 340-line standard that the thread reads once.

The conclusion for the design: the rule is right and the words are nearly right; what is missing is enforcement that does not depend on the model remembering. That is layered below.

### Enforcement layers

From weakest to strongest. Each layer stands alone; together they make delegation the path of least resistance and in-thread work the costly, visible exception.

| Layer | Mechanism | Owner | Where |
| --- | --- | --- | --- |
| 1 Role line | The opener carries the three rules, not a summary of them, and the thread re-bootstraps on request, after a compaction and after a model switch | PMO | `ki-pmo` openers and bootstrap |
| 2 Salience | A hook on every owner message injects one line restating the principle: Claude Code `UserPromptSubmit` and Codex `UserPromptSubmit`, plus a `SessionStart` injection after compaction; it fires only in a coordinating thread and never in an agent `ki agent` launched; the script is shipped by the harness beside its existing hooks and registered through chezmoi in `settings.json` and `~/.codex/hooks/hooks.json` | PMO owns the line; harness ships; chezmoi registers | Decision `COORD-HOOK` |
| 3 Turn budget and self-check | Counted, not judged: at most five tool calls a turn; reads limited to the checkpoint, `ki agent status`, one report and one short file; writes limited to the checkpoint, the decisions log and a brief; anything beyond is a launch; drift is reported to Kris in one line and noted in the checkpoint | PMO | `ki-pmo` |
| 4 Mechanical support | `ki agent` makes delegating cheaper than doing: launch from an inline brief with footer and protocol appended, a detached waiter armed at launch, `recap` since the mark and `brief` from a decision | Delegation and the `ki` command surface | Wave C |
| 5 Lighter coordinator | `fast` at low effort once the gate passes: a coordinator too light to do substantive work well finds doing it slow, poor and visible, while dispatch and bookkeeping stay within reach | Model policy | Decision `COORD-DEFAULT` |
| 6 Acceptance test | Measured in the pilot: while a background agent runs, Kris sends a message; the thread answers within one turn of at most five tool calls, reading nothing beyond the checkpoint and `ki agent status`; `ki agent status` before and after shows the same agents running; the transcript shows no in-session subagent | PMO and the pilot record | Pilot |

The pilot must include layers 1, 2, 3 and 6: the opener, the hook, the counted turn budget and the test. Without the hook the test cannot tell whether words alone hold; without the test nothing is measured. Layer 4 lands in Wave C and layer 5 through the `COORD-DEFAULT` trial, each judged against the same test. The hook's build is sequenced by `COORD-HOOK`, which decides only when it is built and how wide, not whether.

How the hook knows where it is. Both runtimes hand a hook the session identifier, the working directory and the event name. The hook injects only when the working directory is a Capital or harness checkout holding `+/_CHECKPOINTS/` and the process was not launched by `ki agent`, which marks its children by setting an environment variable, for example `KI_AGENT_RUN=<run>`, in both adapters; whether `claude -p` runs hooks at all is _not verified_, and the guard holds either way. The line itself is short, around forty tokens an owner message, and is PMO's text: `Coordinator: delegate every unit of work to a detached background agent; answer this message within one short turn; do not stop or disturb running agents unless the message names one.`

## Summary

The way Kris runs change in the Knowledge Islands territory is sound; its rules are just in the wrong places. The fix is to give each idea one home and one name:

- **Work** says what a record, a Project and an Initiative are and how one record moves. It already exists (`ki-work`, the adapters, `ki-next`, `ki-plan`, `ki-implement`, `ki-accept`, `ki-batch`) and changes least. It keeps the Project registry, and gains one table that defines the three "what for" words: an Initiative's direction, a Project's outcome, a record's goal.
- **PMO** is new, as `ki-pmo`: how the master thread and the Project threads work with Kris. Everything about threads moves here out of `ki-delegation`: openers, the cap and queue, Needs tags, directions, the mark and the roll-up since it. Every Capital declares it.
- **Delegation** (`ki-delegation`) keeps the whole background-run contract from prompt to report, on both the caller's and the worker's side, plus packets. It loses the thread material and gains clearer gates: a run finishing is not the same as succeeding.
- **Continuity** (`ki-checkpoint`) stays the generic checkpoint format with its checker. Openers are generated from the thread name, never stored; the mark becomes a structured field later, once its evidence rule is written.
- **The design loop** keeps its five stages; a record may return to it when a costly choice turns out to be unmade. Its reviews and merge run on the highest-level model of each of two runtimes, every merged report states the models and runtimes used, and the loop says how it degrades when an environment offers less (Kris's models-and-naming instruction). Its name is retested under Kris's rule that a skill name conveys its purpose at a glance: `ki-shape` fails, and decision `NAMES` carries the candidates that pass.
- **Model policy** (`ki-tokenomics`) owns the purposes (`fast`, `standard`, `reasoning`, `frontier`); `ki` owns the per-runtime binding from purpose to model, and binds `frontier` to the highest-level model each runtime offers.

The `ki` commands get one rule: `ki repo` acts on a selection, `ki territory` describes a territory, `ki registry` registers checkouts, `ki agent` runs agents. Two duplicates fold away and two views are added: Projects and threads. "Territory" stays as the word. The coordinator runs on `standard` at low effort by default today, and the pilot trials `fast` at low effort against a written gate, in line with Kris's lean. The pilot is one record: move the thread material into `ki-pmo` without changing its meaning, and prove a fresh session can re-bootstrap from the repository alone. Ten decisions are for Kris; the rest is settled on evidence. Models and environment, below, says who produced each stage and what that means for confidence.

**The principle above the units.** Every unit carries the responsive coordinator (Kris's responsiveness requirement): the thread never does substantive work itself, every unit of work goes to a detached background agent, and an owner message never pre-empts work in flight. The section above diagnoses why the written rule has not held and names six enforcement layers, from the opener's role line to a measured acceptance test, of which the pilot must carry four.

**The test of comprehension.** A new thread reads `ki-pmo`, then `ki-delegation`. A new repository reads `ki-work` and its adapter. Nobody reads `ki-checkpoint` to learn how to coordinate.

## Model

Six units of comprehension. Each is named, bounded, and says what it hands to the others. Where the reviews saw the subject differently, the unit below is the combined reading, with the evidence that settled it.

### Work: what the work is

**Owns.** `ki-work` as selector and shared vocabulary; the adapters `ki-work-roadmap` (the shared record model, declared by every repository), `ki-repo-kb-streams` (placement, zone routing, Enactment and audit for a Knowledge Base), `ki-work-github-issues` and `ki-work-linear` (configuration-only today, with no process executor); the process skills `ki-next`, `ki-plan`, `ki-implement`, `ki-accept` and `ki-batch`; `ki-work-housekeeping` for recurring work; and the Project registry standard with its goal table.

**Boundary.** Everything a record, a Project or an Initiative is, and one record's life in one repository. Nothing about how a thread behaves.

**Hand-offs.** Receives captures from PMO and the design loop through `ki-next`. Exposes records, lifecycle and registry entries to the `ki` views. The registry resolves Project and Initiative slugs for every repository in the territory. A worker's report returns to the lifecycle; it never advances a record by itself.

**Why the registry stays here.** The brief proposed moving the registry standard to `ki-pmo` because only a Capital holds a registry and only coordinating threads act on it. The second premise is false: the rubric that enforces the standard is `ki-work-roadmap/scripts/rubric/contexts/project-registry.ts`, the Streams checker reports close-out due, work-item validation and `--by project` grouping read it, and Project leads own close-out, all without a thread. A standard belongs with its checker and its consumers, so the registry stays in `ki-work`; `ki-pmo` is its principal actor and links to it. "Portfolio" is the top of the Work hierarchy, not a seventh unit.

**Changes.**

- One record format with two placements. `ki-work` says plainly that `ki-work-roadmap` owns the record model for both `docs/roadmap/` and `Streams/Roadmap/`, with `ki-repo-kb-streams` owning the Knowledge Base container, and that Kris's instruction that "every repository adopts the roadmap skill" is met by declaring `ki-work-roadmap` everywhere. No skill merge.
- `ki-repo-kb-streams` retires its duplicate ITERATE, PROPOSE, READY and ROLLOUT entry points in favour of the lifecycle process skills, and aligns its dependency wording with the work-item format's build-order rule.
- Batch is three layers of one concern, documented together: `ki-batch` (the process) names `ki repo batch prepare|validate|run|close` as its mechanics, and `ki-work` keeps owning the `+/_BATCHES/README.md` scaffold, because the `ki-work` declaration is what activates the scaffold, and `ADR-KI-HARNESS-SKILLS-014` makes every process skill invocation-only, so `ki-batch` is never declared and cannot activate or own it.
- The registry standard gains the goal table below, an optional bounded aims list in `## Direction` (decision `AIMS`), an optional short `label` field on the Initiative note so that labels and openers can be derived, permanent acceptance of either note form (file or folder) so a note never moves back after a design folder is deleted, and permission to mention a Project in `## Notes` prose for scope orientation while still forbidding membership lists, record identifiers and status.
- `ki-pulse` moves to `acquire`: it is a process skill that "retains no standing state", holds no standard and triages signals, while `ADR-006` defines `governance` as durable authority standards. The radars stay in `governance`.

### PMO: who drives the work

**Owns.** New governance skill `ki-pmo` in `change-management`, `declaration-only`, declared by every Capital (Kris's review-method instruction): the coordinating thread as a unit. The territory master thread and its Project threads; the cap and the ordered queue; seeding a Project checkpoint; openers and bootstrap as behaviour; directions from the master; the owner-facing reporting practices (banner, Summary, resting point, structured questions, wording), adopting the owner report and its Needs tags from their canonical owner, today the Reporting section of the [`ki-delegation` background-run standard](</Users/krisbrown/workspaces/knowledge-islands/ki-agentic-harness/skills/governance/ki-delegation/references/standards-background-runs.md>), which moves with the rest of the thread material rather than being restated; handoffs under Kris's handoff rule (a handoff stays under Needs as one consolidated message until Kris says it is done); parking tangents; linking records; keeping primary checkouts current; the mark as behaviour and the roll-up since the mark; what a coordinating thread writes into its checkpoint; the coordinator's purpose and the level its escalations require, by reference to Model policy; and the five-word glossary below.

**Reporting forms (Kris's full-summary adoption).** A coordinating thread reports in three forms, each one owner report under the shared banner: the Summary since the owner's last message, the recap since the mark, and the full summary since the thread began, which opens with a `## Decided` list of every owner decision linked to its decisions-log entry, groups `What has been done` by topic, carries dated upcoming deadlines under `Outstanding - no action requested now`, restates every open query in full and closes with a reply block covering them all, with one `DEFAULTS` query for low-stakes choices. The three forms, their windows, their heading levels (H1 banner, H2 sections, H3 queries) and the rule that no form points back to an earlier report are defined in the [`ki-delegation` Reporting section](</Users/krisbrown/workspaces/knowledge-islands/ki-agentic-harness/skills/governance/ki-delegation/references/standards-background-runs.md#full-summary>) and adopted here by reference, not restated; the pilot moves them with the rest of the thread material. Whether the full summary gets a slash-command entry point, and where, is decision `SUMMARY-ENTRY`.

**Boundary.** Coordinating with the owner. Never delivery, never a run's mechanics, never the checkpoint's schema, never the registry's schema. Territorial membership or a Project tag grants no write or acceptance authority in another repository.

**Hand-offs.** Dispatches through Delegation and reads its reports; persists through Continuity; captures through Work; invokes the design loop; hands its definitions table to command centre, which keeps the cross-territory crosswalk and the state-of-play view.

**Rules settled on evidence.**

- A Project thread coordinates exactly one Project. An Initiative's continuing upkeep is delegated from the master, not given a thread of its own, and no Project is invented to give continuing work a thread (decision `THREAD-SCOPE` reconciles the live `rig.chezmoi` thread).
- The cap is Kris's: three Project threads plus the master (the master thread's decision). "Active" means allocated coordination attention, not the existence of a checkpoint or a process; the master's list of eight is reconciled to the cap in the rollout.
- One designated writer per checkpoint: the master may seed an unopened Project checkpoint; once opened, the Project thread owns its updates, and directions from the master go through the `From the master thread` section with a stale-read check, never a simultaneous edit.
- The opener is derived, never stored: `Re-bootstrap as the <project> project thread under ki-delegation.` is the final dot-separated component of the thread name plus fixed text, and `ki` prints it. The master's label-based opener ends with this rule.
- The label is `<Initiative label or title>: <project>`, derived from the registry once the Initiative note carries its optional short label, so the master thread's `Fnd:` and `KI Model:` stand and become checkable. Labels remain presentation only.
- The run-folder history is not durable (Kris's worktree-and-retention rule). A thread's checkpoint carries current state; anything durable is consolidated into Decision Records, notes or records at each mark; a roll-up covers the decisions log, reports and Git since the mark and says so when reports are gone.
- The refresh rule compares the checkpoint's `ki-pmo read at <revision>` with `git log -1 -- skills/change-management/ki-pmo`, so a thread stops checking the wrong skill for changes.
- A coordinator escalates per decision, not per thread: any choice needing analysis, any prompt for ambiguous work and any merge of disputed reports goes to a `reasoning` or `frontier` background agent, as this design did. An escalation uses the highest-level model the environment offers, and independent reviews with a merge use the highest-level model on each of at least two runtimes, today Fable through Claude Code and Astra through Codex; the coordinator dispatches to both and amalgamates the results whichever runtime it runs on itself (Kris's review-method and models-and-naming instructions). The coordinator's own lean default is untouched (decision `COORD-DEFAULT`).

**Responsiveness (Kris's responsiveness requirement).** `ki-pmo` opens with the responsive coordinator principle, in Kris's words, and owns layers 1, 2 (the line), 3 and 6 of its enforcement:

- The opener's role line becomes the three rules, and the thread re-bootstraps on `Re-bootstrap`, after a compaction and after a model switch, re-reading the principle and its checkpoint before anything else.
- The turn budget is counted, not judged: at most five tool calls a turn; reads limited to the checkpoint, `ki agent status`, one report and one short file; writes limited to the checkpoint, the decisions log and a brief. Anything beyond is a launch. Reading a standard, other than at bootstrap or under the refresh rule, is a launch of a reading agent that returns the answer.
- An owner message is answered in the next turn and within the budget. The answer says what is running, what the message changes and what has been launched or queued because of it. A running agent is never stopped by a message that does not name it.
- When the thread notices in-thread work it stops, launches the rest and tells Kris in one line; the same line goes into the checkpoint's `Open questions` as a dated observation, so drift is counted at the next roll-up.
- The salience hook's one line is `ki-pmo`'s text; the hook is built under `COORD-HOOK`.
- The acceptance test is scored from the session transcript in the pilot, not by the rubric, which checks files.

**Rubric.** Thin and complementary to `ki-checkpoint`'s: a Capital has `_state-of-play.md` and no other repository does; each coordinating checkpoint's label matches the registry; the active list is within the cap.

**Glossary (five words, one owner each).** A **session** is one runtime conversation (PMO). A **thread** is a durable, human-named line of coordination that outlives sessions and is rebuilt from its checkpoint (PMO). A **run** is one `ki agent` run folder with its decisions log (Delegation); in PMO's scope "run" never means a `ki-work-housekeeping` recurring-work run or a `ki repo batch` run, which are named in full. A **worker** is one bounded background execution assignment (Delegation). An **agent** is any acting model, including an in-session subagent, which the run standard already distinguishes from a background agent (Delegation).

### Delegation: how work is run

**Owns.** `ki-delegation` in `governance`, reduced: both sides of the background-run contract, caller and worker. Detachment; the run packet and launch metadata; prompt shape; authority tiers, footers and their precedence; the decisions log; coordination between runs; the run queue; monitoring and gates; worker reporting; result reconciliation; and delegation packets for approved high-risk handoffs.

**Boundary.** From prompt to report. It does not select work, choose a model, accept results, or say how a thread talks to its owner.

**Hand-offs.** PMO writes prompts and reads reports; `ki agent` is the launcher and owns runtime flags; Model policy names the purpose a prompt declares; Work owns lifecycle and acceptance.

**Why both sides stay.** The brief kept "only what a launched worker needs"; Astra showed the caller's obligations (prompt, authority, gates, reconciliation) are what make delegation safe, and Fable's own list already includes prompt shape and monitoring. What leaves is the thread material at lines 128 to 253 of the standard, except worker reporting.

**Changes.**

- Three distinct gates, named: the predecessor finished reporting (`DONE`); the required artefact or verification is sufficient; the next action is authorised. `DONE` gives only the first, so a dependent worker validates what it needs before it proceeds, and a watcher never shows an exited worker as a delivered success.
- Authority precedence: a task's narrower instruction wins over its tier's general footer, so a read-only reviewer is representable under a commit-capable footer; the pull-before-commit rule applies only from the `push` tier upward, resolving the conflict with `--rules none`.
- The run packet description names the launcher's extra files; run names are territory-qualified from the start; the worktree location and run-folder retention rules Kris set are written in.
- `ADR-KI-HARNESS-SKILLS-005` and `-006` are refined in place to describe both contracts and the new area boundary, as the design-loop standard requires for an existing record.
- `tools-ki` fixes the footer extraction to find the `## Rules` heading, not its first mention.
- Mechanical support for the responsive coordinator (Kris's responsiveness requirement, layer 4), so that delegating is cheaper than doing: `ki agent launch` accepts an inline brief, by option or standard input, and writes the prompt file, footer and progress protocol itself, so one call launches; the launcher arms a detached `wait --next` so no coordinator waits in the foreground; `ki agent recap <run>` rolls up reports, statuses and the decisions log since the mark into owner-report-shaped text; `ki agent brief <run> <decision>` writes a prompt skeleton from a decision log entry; and both adapters mark their children with an environment variable so the salience hook stays silent in a background agent. **Changes.**

- Model level (Kris's models-and-naming instruction). ### Model policy: which model does what

**Boundary.** Policy, not resolution. It says what purpose a role needs; it does not pick a provider product.

### Coordinator model and effort

Both reviews agree on the shape and differ only on today's default. The shape: a coordinating thread runs on the lightest purpose that can keep authority, scope, decisions and handoffs straight; reasoning is a per-decision escalation to a background agent; `fast` is where this ends up once `ki` carries the bookkeeping (opener, mark, Needs list, roll-up sources); `standard` is the fallback whenever `fast` drops a constraint. Today the bookkeeping is prose a coordinator must judge, and the coordinator is Kris's only interface, so one missed authority boundary costs more than the tokens saved. Kris leans to the lower model (Kris's lean to a lower coordinator model). The merged position is therefore a trial with a gate rather than a switch: `standard` at low effort stays the written default; the pilot's Project thread runs `fast` at low effort against five tests (cold bootstrap, a changed instruction, conflicting reports, a failed predecessor, an unavailable source), judged on missed constraints, owner corrections, delay and total effort rather than coordinator tokens; one missed authority boundary ends the trial on that binding. When the gate passes and the views and mark command exist, `fast` becomes the default (decision `COORD-DEFAULT`).

The lighter model is also an enforcement layer (Kris's responsiveness requirement, layer 5): a `fast` coordinator cannot do substantive work well, so doing it itself is slow, poor and visible, and the economics push it to dispatch. The same lightness cuts the other way, because a lighter model keeps fewer rules in mind, so layer 5 depends on the hook and the counted budget and never replaces them (_inferred_; the trial measures it). The gate gains a sixth test, the responsiveness acceptance test from the pilot run against the `fast` binding, and a pre-empted agent or an in-session subagent ends the trial on that binding as a missed authority boundary does.

Concrete bindings are per runtime and Kris's to choose (decision `BINDINGS`). The model radar (`ki-model-radar`, owner decision of 2026-10-06) records Claude Opus 5.5 through Claude Code and GPT-6.1 Sol through Codex as the adopted default routes, lists GPT-6 Luna as a current API model and Claude Haiku 4.5 under a deprecation watch-item, and binds no route to a `ki-tokenomics` purpose. Astra nominates GPT-6 Luna at low effort for the Codex trial with GPT-6.1 Sol as fallback, as a proposal rather than a verified route.

### Risk to the thread contract

**Kris's words.** The contract says a decision is recorded in Kris's words and, under `CITE-RULE`, "written about what the decision was or is" with no number to fall back on. On this machine a coordinating thread sees those words whole only on the turn they arrive. Every quotation taken from an earlier turn, and every quotation an agent lifts from a transcript or a log through the shell, is a Kompress rendering: function words gone, meaning usually intact, wording never guaranteed. The entry the coordinator wrote for Kris's answers of 23:2x is the first lossy one in the log, and it is marked as such, but the standard has no rule that would have prevented it. `DECISION-HOME` (b), the tracked `+/_THREADS/<thread>/` log, does not help here: it preserves whatever was written, and what was written was already lossy.

**The report shape.** Two instructions tell the model to shorten, and both claim precedence: the `Concise` style says its rules win over "formatting guidance elsewhere", and the shaping block sits at the tail of the system prompt, after every skill. Against them stand the owner report, the Summary, the recap and the full summary, which are nothing but formatting guidance: fixed sections, every query in full, a reply block, no "see earlier". Level 2 and `Concise` together do not forbid the shape, but they reward every cut, and a coordinator under them will drop an empty section, shorten a Summary to a line, or fold the reply block away, which is what Kris calls "formats getting squished". Level 3, if the controller reaches it, removes the Recommendation's "why" outright. The design's layers 1 to 3 restate the shape in the opener and the hook, but a restated rule is still "guidance elsewhere" to a style that says it wins.

**Cadence.** Kris's first question was whether the hook approach captured "the need for regular updates from the coordinator or dispatcher". It did not. The requirement lives in `communication.md` and in `~/.codex/AGENTS.md`: "During work, give a timestamped update (local time, e.g. `20:45 CEST`) at least every few minutes and at each change of activity: one or two plain-language lines on what is happening and what comes next, with no technical detail." The `ki-delegation` standard carries a two-minute cadence for a background agent's status file and says of the owner report that "Under `quiet`, the status-line cadence during work is unchanged", but its Coordinator responsiveness section has no cadence rule, HARN-012 asks the hook for "one line restating the `ki-delegation` responsive-coordinator rules", and the hook line carries only those three rules. The design's layer 2 specifies the line without cadence or format. For a coordinator that truly delegates, the cadence means something narrower than it does for an agent: it has nothing to say between owner messages except that it launched work, that an agent finished, or that it is waiting, and the standard already asks for a Summary "proactively when background agents finish or the owner returns after a gap".
