## Own view

The brief is accurate in nearly every fact and sound in direction. Its weakness is that it answers Kris's request for "something simpler to understand" with eight units, five renames and a new command noun, so the proposed model is more to learn than the current one even though each piece is better placed. The test of comprehension is how many skills a new thread must read to do one thing. Today a coordinating thread reads `ki-delegation`, `ki-checkpoint`, `ki-tokenomics` and the registry standard inside `ki-work`. The design should get that to two: one skill that says how a thread coordinates, and one that says how it delegates.

My proposal keeps three units plus one process:

- **Work** - what the work is: records, Projects and Initiatives, with the registry standard staying in `ki-work` because the checkers that enforce it live in the Work unit. Nothing moves here except the goal table.
- **PMO** - who drives the work: `ki-pmo` owns the coordinating thread end to end, including the checkpoint fields a coordinating thread writes, so `ki-checkpoint` shrinks to a record format with a checker and stops carrying practice.
- **Delegation** - how work is run: `ki-delegation` keeps only the run contract and packets.
- **Design loop** - a process a coordinating thread invokes, kept separate, and renamed only if the rename rides with the PMO wave.

I would remove from the brief's proposal: the Portfolio unit as a separate skill home, the stored `opener` field, the `ki-work-housekeeping` rename, the merge of `ki-repo-kb-streams` into `ki-work-roadmap`, the `ki territory roadmap` alias, and the `ki-shape` name. I would add two things the brief does not mention: the harness decision record that defines the skill areas and describes `ki-delegation` as a packet-only capability is already wrong and must be refined in the same change, and the master thread's `thread-history.md` is a durable record kept only in the non-durable run folder.

On the coordinator model, I agree with the brief against Kris's lean: `standard` at low effort as the default today, `fast` as the target once `ki` carries the thread bookkeeping. The reason is that the bookkeeping is not yet mechanical, so the coordinator still judges, and a wrong judgement by the only thread Kris talks to costs more than the tokens saved.

## Proposed structure

Named units, each with its boundary and hand-offs. Four units; two are unchanged.

**Work** (`change-management`): `ki-work` as selector, vocabulary and home of the registry standard with the goal table; adapters `ki-work-roadmap`, `ki-repo-kb-streams`, `ki-work-github-issues`, `ki-work-linear`; process skills `ki-next`, `ki-plan`, `ki-implement`, `ki-accept`, `ki-batch`; `ki-work-housekeeping` unchanged. Boundary: everything a record, a Project or an Initiative is, and one record's life. Hand-offs: receives captures from PMO and the design loop through `ki-next`; exposes status for `ki` views; the registry resolves slugs for every repository in the territory. Change: the goal table (direction, outcome, goal) and the bounded aims list are added to the registry standard; the batch scaffold moves to `ki-batch`; the standard states that one record format has two placements.

**PMO** (`change-management`, new `ki-pmo`, governance, declaration-only, declared by every Capital): the coordinating thread as a unit. Owns the four words session, thread, run and agent; the territory master thread, Project threads, cap and queue, seeding; openers and bootstrap as behaviour, with the opener derived from the thread name; directions; Summary, banner, resting point; Needs tags and handoffs (Decision 6); parking; linking records; keeping primary checkouts current; the mark as behaviour and the roll-up since the mark; coordinator purpose by reference to `ki-tokenomics`; what a coordinating thread writes into its checkpoint. Boundary: coordinating with the owner; never delivery, never a run's mechanics, never the checkpoint's schema. Hand-offs: dispatches through Delegation, persists through `ki-checkpoint`, captures through Work, invokes the design loop. Rubric: `_state-of-play.md` exists in a Capital; coordinating checkpoint labels match the registry.

**Delegation** (`governance`, `ki-delegation` reduced): detachment, run packet, prompt shape, authority tiers and footers, decisions log, coordination, run queue, monitoring, worker reporting, delegation packets. Boundary: from prompt to report. Hand-offs: PMO writes prompts and reads reports; `ki agent` is the launcher; `ki-tokenomics` names the purpose a prompt declares. Change: lines 128 to 253 leave; ADR-SKILLS-005 and ADR-SKILLS-006 are refined to describe both contracts.

**Continuity** (`governance`, `ki-checkpoint` unchanged in role): the record format and lifecycle for any named thread, with a checker. Change: one optional `mark` field (`at`, `decision`) in a second wave; the prose cross-references to the delegation standard re-point to `ki-pmo`. No `opener` field.

**Design loop** (`change-management`, `ki-design-loop`, possibly `ki-deliberate`): unchanged process, invoked by a coordinating thread, handing its rollout to `ki-next`. The `design/` folder convention is unchanged whatever the skill's name.

**Not units:** `ki-recap` stays the single-session summary and keeps its `checkpoint <thread>` composition. `ki-tokenomics` owns purposes and the repository's preference; the operator's purpose-to-model binding lives with `ki`. `ki-pulse` moves to `acquire`.

**Goal hierarchy.** One table in the registry standard: an Initiative has a `direction` (never met) and three to five aims inside `## Direction` that name no Project; a Project has an `outcome` (met once, with a test); a record has a `## Goal` (met by one change). Links point upwards; `ki repo projects` derives the downward view.

**Command surface.** `ki repo` acts on a selection and gains `list`, `projects` and `threads`; `ki territory` keeps `list`, `audit`, `roots` and `inspect` and loses `show` and `open`; `ki registry` manages registration and loses the selectors it does not need; `ki agent launch` keeps `--model` and `--effort` and gains `--purpose` resolved through user-level bindings per runtime. "Territory" stays as the word; an alias is optional.

**Coordinator default.** `standard` at low effort for the master and Project threads, stated once in `ki-tokenomics`; `fast` becomes the default when `ki repo threads`, a mark command and a Needs listing exist. Reasoning is a per-decision escalation to a background agent.

**Simplest to understand.** A new thread reads `ki-pmo` and then `ki-delegation`. A new repository reads `ki-work` and its adapter. Nobody reads `ki-checkpoint` to learn how to coordinate.

**What I would remove.** The Portfolio unit as a home, the `opener` field, the `ki-work-housekeeping` rename, the adapter merge, the `ki territory` views and roadmap alias, `ki-shape`, and the two-skill pilot.
